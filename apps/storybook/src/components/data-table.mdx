# Data table

Data table is the one table for lists people work through: selection in the
first column, six cell types, sorting, search and filters, locked rows that
say why, and columns pinned to either edge. TanStack Table works out the rows
and keeps the state; Data table draws them in a native table that matches the
Data table in the Figma library.

<Canvas of={Stories.Default} />

## Features

- One hook, `useDataTable`, takes your rows and columns. Sorting, search,
  filters with counts, pages, selection and which columns show all work
  without code of your own.
- A checkbox column with select all, which skips locked rows and shows a
  dash while only some rows are selected. Select all matching reaches the
  rows on other pages.
- Shift+click selects a range, in the order the rows are shown, and Escape
  clears the selection.
- Six cell types: primary, text, person, status, numeric and actions. A
  second line on a cell makes its row 52 pixels.
- Columns pinned to the start or end, with shadows while there's more to
  scroll. Pinning switches off under 32rem.
- Sorting, search, filters and the page can live in the URL, so a link opens
  the same view.
- Selection changes are announced: “3 members selected”, “Selection cleared”.
- One toolbar row for every action: search, filters and create actions while
  idle, then the selection and bulk actions in the same place while rows are
  selected.
- Under 32rem it keeps working: the table scrolls under an icon-only
  toolbar, or each row becomes a card read from the same rows. Filters move
  into a sheet.

## Usage

```tsx
import { Badge } from "@/components/ui/badge"
import {
  createDataTableColumnHelper,
  DataTable,
  DataTableContent,
  DataTableFilters,
  DataTableSearch,
  DataTableToolbar,
  useDataTable,
} from "@/components/ui/data-table"

// Outside the component, so the rows aren't worked out again every render.
const column = createDataTableColumnHelper<Member>()
const columns = column.columns([
  column.accessor("name", {
    header: "Member",
    meta: {
      type: "person",
      avatar: (member: Member) => ({
        src: member.photo,
        fallback: member.initials,
      }),
    },
  }),
  column.accessor("status", {
    header: "Status",
    filterFn: "arrHas",
    meta: { type: "status" },
    cell: ({ getValue }) => <Badge variant="success">{getValue()}</Badge>,
  }),
])

export function Members({ members }: { members: Member[] }) {
  const table = useDataTable({
    data: members,
    columns,
    lockedReason: (member) =>
      member.isOwner ? "The workspace owner can't be removed" : undefined,
    initialState: { columnPinning: { start: ["name"], end: [] } },
  })
  return (
    <DataTable
      table={table}
      aria-label="Members"
      noun={{ one: "member", other: "members" }}
    >
      <DataTableToolbar>
        <DataTableFilters
          search={<DataTableSearch aria-label="Search members" />}
        />
      </DataTableToolbar>
      <DataTableContent />
    </DataTable>
  )
}
```

Every row needs an `id`, or pass `getRowId`: selection is kept by id, so it
survives sorting, filtering and paging. Keep `columns` and `data` stable
between renders. A column's `meta` sets how it draws:

```ts
type DataTableColumnMeta = {
  type?: "primary" | "text" | "person" | "status" | "numeric" | "actions"
  label?: string // in the Columns menu, filters and cards
  className?: string // on the head and every cell, such as a width
  secondary?: (row: Row) => ReactNode
  avatar?: (row: Row) => { src?: string; fallback: string } | undefined
  icon?: ReactNode
}
```

The first primary or person column names each row's checkbox. Every row
shows until you give the table a page size, in
`initialState.pagination` or a pagination atom, and put DataTablePagination
in the footer.

### Reading and owning state

The component that calls `useDataTable` doesn't re-render when the state
changes; each part subscribes to what it shows, so ticking a row re-renders
that row and the toolbar, not the table. To read state there, pass a
selector, `useDataTable(options, (state) => state.rowSelection)`, and read
`table.state`, or use `table.Subscribe`. Act on the selection with
`table.getSelectedRowIds()` and `table.resetRowSelection()`. The selection
holds only rows in the data that match the filters: ids a refetch drops or
a filter hides leave it, so the count and the ids agree. With
`manualPagination`, ids on other pages stay, since the app owns those.

Sorting, column filters, the search and the page can be owned outside the
table, as atoms. `useSearchParamsAtom` keeps one in the URL with
`history.replaceState`, so typing a search doesn't fill the back button. It
starts from the empty value on the server and in the first render, so
hydration matches, and applies the URL's value once mounted, before paint:

```tsx
const sorting = useSearchParamsAtom("sort", dataTableCodecs.sorting)
const globalFilter = useSearchParamsAtom("q", dataTableCodecs.text)
const columnFilters = useSearchParamsAtom(
  "filters",
  dataTableCodecs.columnFilters
)
const pagination = useSearchParamsAtom("page", dataTableCodecs.pagination(25))

const table = useDataTable({
  data,
  columns,
  atoms: { sorting, globalFilter, columnFilters, pagination },
})
```

Selection, column visibility and pinning stay in the table. For rows that
page on a server, set `manualSorting`, `manualFiltering`,
`manualPagination` and `rowCount`, and load the rows the atoms describe.

### Features

`dataTableFeatures` registers only what Data table uses, so a table carries
nothing else: sorting (`text`, `alphanumeric`, `basic` and `datetime`
comparators), column and global filtering (`includesString`, `equals` and
`arrHas`), faceted unique values, pagination, row selection, column
visibility and column pinning. Grouping, expanding, resizing, ordering and
row pinning are left out.

## Migrating to the table API

The `rowIds`, `totalCount`, `value`, `defaultValue` and `onValueChange` props,
`useDataTableSelection`, and hand-written `DataTableRow`, `DataTableCell` and
`DataTableHead` are deprecated in 0.2.0 and removed in 0.3.0. Until then
they run on the same TanStack table as the new API, built from `rowIds` with
selection only, so they behave as they did.

A codemod lists every use with its file and line. It changes nothing:
writing column definitions needs a person.

```sh
pnpm dlx jscodeshift --parser tsx --dry \
  -t https://fibo.toribryan.com/codemods/data-table-legacy-api.js src
```

```tsx
// Before
const selection = useDataTableSelection()
;<DataTable rowIds={members.map((m) => m.id)} {...selection}>
  <DataTableContent>
    <DataTableHeader>
      <DataTableHead type="person" pinned="start">
        Member
      </DataTableHead>
    </DataTableHeader>
    <DataTableBody>
      {members.map((m) => (
        <DataTableRow key={m.id} id={m.id} lockedReason={m.lock}>
          <DataTableCell type="person" pinned="start">
            {m.name}
          </DataTableCell>
        </DataTableRow>
      ))}
    </DataTableBody>
  </DataTableContent>
</DataTable>

// After
const table = useDataTable({
  data: members,
  columns, // column.accessor("name", { header: "Member", meta: { type: "person" } })
  lockedReason: (m) => m.lock,
  initialState: { columnPinning: { start: ["name"], end: [] } },
})
;<DataTable table={table}>
  <DataTableContent />
</DataTable>
```

## API reference

DataTable takes `table` from useDataTable, plus `noun`, `narrowLayout` and
Show selected only. `useDataTable` takes TanStack Table's options for
`dataTableFeatures`, `data` and `columns` among them, plus `lockedReason`;
column `meta` is `DataTableColumnMeta` (see [Usage](#usage)). Every part also
takes the props of the element it renders. The deprecated props are listed
for the one release they remain.
